# Upvest Investment API integration plan — eShopOnWeb managed investment portfolios

Plan-first artifact for the `dotnet-integrate-upvest-investment-api` workflow. It records the Upvest **call surface** (signatures, wire shapes, errors) and the application decisions the SDK forces. All Upvest facts are grounded in the SDK map/source bundled in this plugin.

- **SDK root** (plugin-relative, read-only, also the build reference): `plugins/upvest-v4/sdk/dotnet/`. Every `Source` path below is relative to that root.
- **Target project**: `src/PublicApi` (RootNamespace `Microsoft.eShopWeb.PublicApi`). Endpoints follow the `MinimalApi.Endpoint` `IEndpoint<…>` pattern (exemplar: `src/PublicApi/CatalogItemEndpoints/CreateCatalogItemEndpoint.cs`), registered by `AddEndpoints()` / `MapEndpoints()` in `src/PublicApi/Program.cs`.
- **Persistence**: in-memory EF (`UseOnlyInMemoryDatabase=true`, see `src/Infrastructure/Dependencies.cs`) via generic `IRepository<T>` / `EfRepository<T>` over `CatalogContext`. Data is lost on restart and the store is per-host isolated.
- **Spec version**: SDK generated from Upvest spec `1.172.0`; all operations are **Case A (typed errors)**, **throw-only**, **no pagination helper** (offset/limit query params only).

> ⚠ **Sandbox scope limit (environment, not a bug, not a gap):** the provided credentials authorise ONLY *user operations* scopes (`users:read`/`users:admin`). Every call whose **Auth** bullet needs another scope (`accounts:*`, `portfolios:*`, `payments:*`, `tests:*`, `taxes:*`, `positions:read`, `valuations:read`) returns `401 "This client is not authorised to use these scopes"` at runtime. Those paths are built in full and marked **UNVERIFIED** — design is complete, only live confirmation is blocked. See each row's source cell and §6.

## 1. Scope & sequence

The eShop concept → Upvest concept mapping:

| eShop concept | Upvest concept |
| --- | --- |
| Investor (a signed-in shopper) | **User** (BYOL operating model) + a **PERSONAL account group** + a **PORTFOLIO-type account** |
| Model portfolio (name + funds[{ISIN, weight}], weights = 100) | **Portfolio allocation** (`PortfoliosAllocation`: `name` + `allocation[]` of `{instrument_id, weight}`) |
| Investor "follows a model" | **Portfolio configuration** (`PortfoliosConfiguration`: links `account_id` → `allocation_id`) |
| Paying in | sandbox cash-in (`Tests.CreateBankTransaction`) **then** a BUY **portfolio order** (`PortfoliosOrder`) that invests cash across the allocation |
| Realignment | **Portfolio rebalancing execution** (`TriggerPortfolioRebalancing` by allocation) |
| Portfolio holdings/value | **Account valuation** (`GetAccountValuation`: `security_positions[]` + `total_security_value`) |

The application keeps its own records (in-memory EF): a per-shopper **InvestorRecord** (eShop buyerId → Upvest userId / accountGroupId / accountId, + sign-up status), a **ModelPortfolioMap** (shop `modelId` ↔ Upvest `allocationId`), a per-payment **PaymentRecord** (paymentId → Upvest portfolio-order id, amount, status), and a **RealignmentRecord** (realignmentId → Upvest execution id). These bridge the shop's own identifiers to Upvest UUIDs; without them the shop cannot resolve `{modelId}` or scope records to one shopper.

Implementation steps, each naming the Upvest operations it uses:

1. **Client wiring & auth** — register `UpvestInvestmentApiClient` (DI singleton), OAuth2 client-credentials + the mandatory HTTP message-signing hook, base URL from config, fail-fast credential check. (No operation yet.) → `dotnet-client-initialization`, `dotnet-authentication`.
2. **App records & repositories** — add the four entities above to `ApplicationCore.Entities` + `CatalogContext`; expose via `IRepository<T>`. Primary keys chosen so a duplicate claim is refused by the store (see DUPLICATE CLAIMS).
3. **Flow 1 — Become an investor** — `POST /api/portfolio/investor` → `Users.CreateUser` (BYOL) → `UserIdentifiers.CreateIdentifier` (identity document) → `TaxResidencies.SetTaxResidencies` (tax) → `AccountGroups.CreateAccountGroup` (PERSONAL) → `AccountsApi.CreateAccount` (type PORTFOLIO). `GET /api/portfolio/investor` → `Users.RetrieveUser` + `AccountGroups.RetrieveAccountGroup` (readiness).
4. **Flow 2 — Model portfolios** — `PUT /api/portfolio/models/{modelId}` → `Portfolios.CreatePortfoliosAllocation` (first time) or `Portfolios.UpdatePortfoliosAllocation` (replace). `GET /api/portfolio/models` → `Portfolios.ListPortfoliosAllocations`. `PUT /api/portfolio/investor/model` → `Portfolios.CreatePortfoliosConfiguration` or `Portfolios.UpdatePortfoliosConfiguration`.
5. **Flow 3 — Pay in** — `POST /api/portfolio/payments` → `Tests.CreateBankTransaction` (sandbox cash-in) → `Portfolios.CreatePortfoliosOrder` (BUY). `GET /api/portfolio/payments` → app records, status refreshed via `Portfolios.RetrievePortfoliosOrder` / `Portfolios.ListPortfoliosOrders`.
6. **Flow 4 — Realignment** — `POST /api/portfolio/models/{modelId}/realignments` → `PortfoliosRebalancing.TriggerPortfolioRebalancing` (Allocations arm). `GET /api/portfolio/realignments/{realignmentId}` → `PortfoliosRebalancing.RetrievePortfoliosRebalancingExecution` + `PortfoliosRebalancing.ListPortfolioRebalancingExecutionOrders` (derive status).
7. **Flow 5 — Portfolio** — `GET /api/portfolio` → `Portfolios.RetrievePortfoliosConfiguration` (current `allocation_id` → shop modelId) + `Valuations.GetAccountValuation` (holdings + total value); `paidIn` from the app's own PaymentRecords.

## 2. CONTRACT SHEET

> ⚠ **Signatures below are generated code, verbatim.** Every operation that takes input takes **ONE request record as its first parameter** (`client.{Group}.{Operation}(new {Operation}Request { … }, requestOptions?, cancellationToken?)`), built with an **object initializer whose property names are the record's own** — never flat positional arguments. An operation with no inputs takes no request record.
> ⚠ **Every SDK type is written fully-qualified**, with the namespace its source path implies (`Models/` → `UpvestInvestmentApi.Models`; `Models/AnyOf/` → `UpvestInvestmentApi.Models.AnyOf`; `Models/Enums/` → `UpvestInvestmentApi.Models.Enums`; `Requests/<Ctrl>/` → `UpvestInvestmentApi.Requests.<Ctrl>`; `Errors/` → `UpvestInvestmentApi.Errors`). Take each type's namespace from the path the map gives for **that** type, never from a neighbour.

Shared to all rows: **error Case A** — `ApiException<{Operation}Error>` exposing `.Error.TryGetNoContent(out RawError? v)` (covers the non-2xx statuses listed per op) and the inherited `.Error.TryGetRawError(out RawError? v)` fallback; `RawError` has `StatusCode`, `ReadAsString()`, `ReadAsJson<T>()`. Request records also carry `UpvestApiVersion UpvestApiVersion { get; init; } = UpvestApiVersion._1` (optional; default is fine). `RequestOptions? requestOptions = null, CancellationToken cancellationToken = default` are omitted from the signatures below for brevity.

### 2b. CROSS-OPERATION INVARIANTS

| Invariant | Operations | Enforced where |
| --- | --- | --- |
| The `instrumentId` (ISIN) of every fund in a model PUT must be a real Upvest instrument | `CreatePortfoliosAllocation`/`UpdatePortfoliosAllocation` (rows 8/9) ← `client.Instruments.ListInstruments`/`RetrieveInstrument` (`map/operations/Instruments.md`) | Validate each ISIN via `RetrieveInstrument` (scope `instruments:read`) in the model PUT handler **before** the allocation write; reject unknown ISINs with 400. (Falls under instruments scope → UNVERIFIED in sandbox; still coded.) |
| The sum of `weight` across a model's funds must equal exactly 100 | `CreatePortfoliosAllocation`/`UpdatePortfoliosAllocation` (rows 8/9) — rule is the application's (task), the SDK only regex-validates each weight 0–100 | In the model PUT handler, before the allocation write: parse weights and assert they total `100` exactly; reject otherwise. |
| The `modelId` a shopper picks (`PUT /investor/model`) and the `modelId` in a realignment POST must be one that `GET /api/portfolio/models` offers | `CreatePortfoliosConfiguration`/`UpdatePortfoliosConfiguration` (rows 11/12) and `TriggerPortfolioRebalancing` (row 18) ← **ModelPortfolioMap** (the app's store, populated from `CreatePortfoliosAllocation` row 8) | In the investor-model PUT and realignment POST handlers, look the shop `modelId` up in ModelPortfolioMap to resolve its Upvest `allocationId`; a `modelId` with no mapping → 404/400 before any Upvest call. The map read is part of the work. |
| The `account_id` in a configuration/order/valuation must be the caller's own account | rows 11,12,13,15,16,17,21 ← **InvestorRecord** (the app's store, populated in Flow 1) | Every per-shopper endpoint resolves the caller's `accountId`/`userId` from InvestorRecord keyed by the authenticated buyerId; never from the request body. Enforces one-shopper-one-portfolio isolation. |
| A payment/portfolio-order requires the caller to be an accepted investor **with a model chosen** | `CreatePortfoliosOrder` (row 15) ← InvestorRecord (status active) + `RetrievePortfoliosConfiguration` (row 13) | In the payment handler, before cash-in/order: assert InvestorRecord status is active AND a configuration (chosen model) exists; refuse with 409/422 otherwise. |

**Status mapping the application exposes (names FIXED by task):**
- **Sign-up** `status`: `pending` until Upvest has accepted the user AND the PORTFOLIO account is ready (user `Status` not OFFBOARDED/INACTIVE AND account-group status ACTIVE per `UserByol.Status` docs); `active` once ready; `rejected` if Upvest rejects onboarding. (Derivation is the app's — `YOUR CALL — not in the map`, settled against task at impl; the readiness signal is read from rows 1/5/7.)
- **Payment** `status`: `pending` while order `Status65` ∈ {NEW, PROCESSING}; `invested` at {FILLED, SETTLED}; `failed` at {CANCELLED}. (`YOUR CALL` mapping; vocab fixed by task.)
- **Realignment** `status`: `pending` until all execution orders (row 20) are terminal; `completed` if all succeeded; `failed` if any failed. (`YOUR CALL` — the execution resource carries no status, see trap T5.)

### 2d. Client construction, auth, server node

- **Client**: `UpvestInvestmentApi.UpvestInvestmentApiClient(HttpClient httpClient, UpvestInvestmentApi.UpvestInvestmentApiClientOptions options)` — the only constructor. Register once as a **singleton**; own the `HttpClient` lifetime deliberately (→ `dotnet-client-initialization`). API groups are properties: `client.Users`, `client.AccountGroups`, `client.AccountsApi`, `client.Portfolios`, `client.PortfoliosRebalancing`, `client.Tests`, `client.Valuations`, `client.UserIdentifiers`, `client.TaxResidencies`, `client.Instruments`, `client.Positions`.
- **OAuth2 (client credentials)**: `options.OauthClientCredentials = new UpvestInvestmentApi.Core.Authentication.OAuth2.ClientCredentials.OAuth2ClientCredentials { ClientId = <Upvest:ClientId>, ClientSecret = <Upvest:ClientSecret> }`. One token minted per scope set; token endpoint derives from the base URL.
- **HTTP message signing (mandatory on EVERY call, including the token request)**: `options.Hooks = [ new UpvestInvestmentApi.Signing.UpvestSigningHook( UpvestInvestmentApi.Signing.UpvestHttpSignatureCredentials.FromFile(keyId: <Upvest:SigningKeyId>, privateKeyPath: <Upvest:SigningKeyPath>, upvestClientId: <Upvest:ClientId>, privateKeyPassphrase: <Upvest:SigningKeyPassphrase>)) ]`. If neither a hook nor the signing env vars are present, **every call throws `InvalidOperationException` before it is sent**. → `dotnet-authentication`.
- **Environment / base URL**: `options.Environment = UpvestInvestmentApi.Servers.ServerEnvironment.Production` (= sandbox `https://sandbox.upvest.co`). Override the base address from config: `options.Server.Default.Production.BaseUrl = <Upvest:BaseUrl>`. Single server group `Default`.
- **Config binding** (bind from the `Upvest:` section; env vars fill these keys; hard-code nothing): `Upvest:ClientId`, `Upvest:ClientSecret`, `Upvest:SigningKeyId`, `Upvest:SigningKeyPath`, `Upvest:SigningKeyPassphrase`, `Upvest:BaseUrl`. Secrets (`ClientSecret`, `SigningKeyPassphrase`) load into user-secrets from env; never in source/logs/responses.

## 3. Trap notes

- **T1 (all call sites)** — the response model returns **only** the deserialized body; HTTP status/headers of a success are not on it. A drifted 2xx (missing `required`) or a non-2xx body not matching `{Operation}Error` surfaces as `ResponseDeserializationException`, which is **not** `ApiException<TError>`. **MUST load `upvest-v4:dotnet-error-handling`.**
- **T2 (auth wiring, step 1)** — OAuth2 alone is insufficient; the signing hook is required or the client throws before the wire. Which env vars the hook reads, and precedence of code vs env values, decide whether your config actually applies. **MUST load `upvest-v4:dotnet-authentication`.**
- **T3 (client DI, step 1)** — who owns the `HttpClient`, and the singleton's effect on a rotated secret, are not visible in the constructor signature. **MUST load `upvest-v4:dotnet-client-initialization`.**
- **T4 (money amounts, rows 8/14/15/21)** — Upvest amounts/weights/quantities are **decimal strings** with their own regexes, not JSON numbers; the task's wire contract is JSON numbers in euros with 2 dp. Converting across this boundary (rounding, culture-invariant formatting, the 2-dp bank-transaction regex vs the 27-dp order regex) is where correctness is lost. Formatting rules: **MUST load `upvest-v4:dotnet-models`.**
- **T5 (realignment status, rows 19/20)** — `PortfoliosRebalancingExecution` has **no status field**; the retrieve call alone cannot report `completed`/`failed`. Status must be derived from the execution orders list. Deriving it is application logic, not an SDK fact — treat as `YOUR CALL` and confirm the per-order status member in the list-item file at impl.
- **T6 (unions, rows 1,4,6,18)** — request bodies are `AnyOf` unions; pick the correct arm (BYOL user, user account-group/account, Allocations rebalancing) via the static factory or implicit conversion; a wrong arm serializes a wrong shape that the server rejects. Union build/read semantics: **MUST load `upvest-v4:dotnet-models`.**
- **T7 (retries/timeouts/pagination, steps 3–7)** — what `Retry.Timeout` bounds vs the per-attempt timeout, which verbs are retried, and that list reads are offset/limit (no auto-pager) all affect duplicate writes and partial reads. **MUST load `upvest-v4:dotnet-configuration-resilience`.**
- **T8 (sensitive data, Flow 1)** — the sign-up carries personal data (name, birth, address, tax id, document number). SDK request-body logging is verbatim when on, and the `UPVEST_INVESTMENT_API_LOG=trace` env var can force it with no code change. Keep `LogRequestBody` off and set `LoggerFactory` explicitly. **MUST load `upvest-v4:dotnet-configuration-resilience`.**
- **T9 (testing, step 8)** — the HttpClient stub seam and constructing SDK exceptions directly are needed to test the 401/`ResponseDeserializationException`/unknown-outcome paths without live traffic. **MUST load `upvest-v4:dotnet-testing`.**

**Always-present hazard row:** a body that does not match its declared type — a drifted or malformed **2xx** (a missing `required` member) or a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape — surfaces as `ResponseDeserializationException`, an `ApiException` that keeps the HTTP status and names the target type but is **not** an `ApiException<TError>`. A catch ladder that handles only `ApiException<TError>` lets it escape, so it must also catch `ResponseDeserializationException` (or `ApiException`).

## 5. PRODUCTION READINESS

| # | Concern | Decision |
| --- | --- | --- |
| 1 | **Credential fail-fast** | Bind the 6 `Upvest:*` keys via `IConfiguration` at startup. The host refuses to start (throw in the DI registration / an `IStartupFilter`) when **any** of `Upvest:ClientId`, `Upvest:ClientSecret`, `Upvest:SigningKeyId`, `Upvest:SigningKeyPath`, `Upvest:SigningKeyPassphrase`, `Upvest:BaseUrl` is missing or blank — each part checked separately (a blank signing passphrase is not a missing one, but a blank key path is fatal). This pre-empts the `InvalidOperationException` (missing signing) / `AuthSchemeException` (missing OAuth) that would otherwise appear only on the first call. Signing-key file existence/readability also checked. |
| 2 | **Secret sourcing & rotation** | Secrets come from env → user-secrets (never repo). The DI builds `UpvestInvestmentApiClientOptions` **once at registration** and captures it in the singleton client, so a rotated `ClientSecret`/`SigningKeyPassphrase`/key file takes effect only on process restart. Rotation-without-restart is **not required** here (in-memory, restart-tolerant deployment); documented as restart-to-rotate. |
| 3 | **Total timeout budget** | The caller-facing budget is the SDK retry window, not a single knob: set `options.Retry` (`MaxRetries`, `Delay`, `Timeout`, backoff) so worst-case total ≈ per-attempt timeout × (1+MaxRetries) + backoff; flow handlers pass the ASP.NET request `CancellationToken` to every call. Exact meaning of `Retry.Timeout` vs per-attempt bound confirmed via `dotnet-configuration-resilience` before setting numbers. `YOUR CALL` on the numbers, settled at impl. |
| 4 | **Write-retry ownership** | Default retry set (confirm in `dotnet-configuration-resilience`) typically retries idempotent/safe verbs on 5xx/429. All Upvest writes here are POST/PUT carrying a real `IdempotencyKey` member (rows 1,3,4,6,8,11,12,14,15,18), so provider-side replay is safe; decide per-row whether to leave SDK retry on. GET reads (rows 5,7,10,13,16,17,19,20,21) freely retried. |
| 5 | **Idempotency & ambiguous writes** | Real keys exist: every write's request record carries a required `IdempotencyKey: Guid` (rows 1,3,4,6,8,11,12,14,15,18) — this is the reconciliation key, **derived deterministically from the application's own claim** (e.g. a GUID stored on the PaymentRecord/InvestorRecord) so a retry reuses it. `UpdatePortfoliosAllocation`/`RetrieveAccount` etc. that take only a path id are naturally idempotent. The injected `Idempotency-Key` **header** is a fresh GUID per call and is NOT a key — never cited. Reconciliation path per write in UNKNOWN OUTCOMES. |
| 6 | **Observability** | Structured logs at Information for each flow milestone (investor created, model saved, payment placed, realignment triggered) keyed by the app's own ids; Warning/Error on `ApiException`/`ResponseDeserializationException`/`SdkConnectionException` carrying the provider correlation id read from `RawError.ReadAsString()`/`ReadAsJson<T>()` (and the operation name the exception names). **No personal data and no request bodies in logs** (see #7). |
| 7 | **Sensitive data** | Flow 1 carries personal data (name, DOB, address, phone, taxId, document number). Posture: `options.Logging.LogRequestBody` stays **off**; `options.Logging.LoggerFactory` set **explicitly** (disarms the `UPVEST_INVESTMENT_API_LOG=trace` body-logging backdoor); application diagnostics never echo a sign-up/identifier/tax request body; add any form-body sensitive keys to the deny-list if form logging is ever enabled. |
| 8 | **Environment selection** | Single server group `Default`. `ServerEnvironment.Production` = sandbox `https://sandbox.upvest.co`; `ServerEnvironment.Environment2` = live `https://api.upvest.co`. This deployment sets `options.Environment = Production` and overrides `options.Server.Default.Production.BaseUrl` from `Upvest:BaseUrl` (sandbox). A live deployment would switch the environment and point `Upvest:BaseUrl` at the live host. Test traffic is kept off live by the config value alone — document that `Upvest:BaseUrl` must never be a live host in non-prod. |
| 9 | **Duplicate prevention under concurrency** | See DUPLICATE CLAIMS. The app owns an in-memory EF store; a primary-key insert is refused even by the in-memory provider, so claims use PKs. |
| 10 | **Partial results** | See PAGED READS. All Upvest lists are offset/limit with a `meta.total_count`; the app pages to completion or caps and signals truncation in its own response. |
| 11 | **Unknown outcomes** | See UNKNOWN OUTCOMES. Every write is re-readable by the id it returns (order id, execution id, user id, allocation id) or by the deterministic idempotency key; a connection failure after send is settled by re-read in the write's own catch, or the app record is marked `unknown` for later reconciliation. |

## 6. Assumptions & Blockers

**Assumptions**

- **BYOL operating model** chosen for `Users.CreateUser` (arm `UserByolCreateRequest`): the shop verified the shopper's identity itself, which is the Bring-Your-Own-Licence model; it does not require the TOL-only `fatca`/consent objects. If the Upvest sandbox client is provisioned as **TOL**, switch to `UserTolCreateRequest` (adds required `fatca`, `terms_and_conditions`, `data_privacy_and_sharing_agreement`, and uses `Address2`). Verifiable against sandbox (user scope authorised).
- **identityDocument.expiryDate has no home in the SDK.** `IdentifierCreateRequest` (row 2) carries only `type`, `issuing_country`, `identifier` (number) — no expiry date. The app will capture `expiryDate` in its own InvestorRecord and submit only type/number/issuingCountry to Upvest. `identityDocument.type` maps to `Type7` (NATIONAL_ID/PASSPORT); any other value is rejected at the shop boundary.
- **taxId/taxCountry** are submitted via `TaxResidencies.SetTaxResidencies` (row 3), not the user-create body. (Scope `taxes:admin` → UNVERIFIED in sandbox.)
- **"Account able to hold a managed portfolio"** = a `PERSONAL` account group + an account of **type `PORTFOLIO`** (`Type16.Portfolio`); the task's managed portfolio requires the portfolio-basis account type (per `AccountCreateUserRequest.type` docs). An order/allocation/configuration on a TRADING account would be rejected.
- **Pay-in mechanism (`YOUR CALL — not in the map`):** modeled as sandbox cash-in via `Tests.CreateBankTransaction` **then** a BUY `CreatePortfoliosOrder`. Upvest also offers auto-investment of incoming cash (`PortfoliosOrder.initiation_flow = AUTO_INVESTMENT`) and `TopUps.CreateTopup`; the exact "whatever Upvest provides" cash-in path for a PORTFOLIO account cannot be confirmed in sandbox (payments/tests scopes unauthorised). The order BUY path is the primary invest action; the cash-in call is isolated so it can be swapped. Settle at impl against sandbox behaviour.
- **Status derivations** (sign-up pending/active/rejected; payment pending/invested/failed; realignment pending/completed/failed) are application mappings over Upvest fields (`YOUR CALL — not in the map`), since Upvest exposes richer/other vocab (and no status at all for a rebalancing execution — see trap T5). The **exposed field names and vocab are fixed by the task**; only the derivation is the app's.
- **Realignment status** is derived from `ListPortfolioRebalancingExecutionOrders` (row 20) because `PortfoliosRebalancingExecution` (row 19) has no status field. Confirm the per-order status member in `PortfoliosRebalancingExecutionOrderListResponse.cs` at impl.
- **Caller identity** comes from the JWT (`HttpContext.User`); each per-shopper endpoint resolves the caller's buyerId → InvestorRecord and never trusts a user/account id from the request body (enforces one-shopper isolation). Admin-only endpoints (model PUT, realignment POST) use `[Authorize(Roles = BlazorShared.Authorization.Constants.Roles.ADMINISTRATORS)]` exactly as `CreateCatalogItemEndpoint` does; all others use `[Authorize(AuthenticationSchemes = JwtBearerDefaults.AuthenticationScheme)]`.
- **In-memory persistence** means InvestorRecord / ModelPortfolioMap / PaymentRecord / RealignmentRecord are lost on restart and isolated per host. After a restart the shop cannot resolve old `{modelId}` → `allocationId` or scope old payments; acceptable per the task's stated environment, but noted because it weakens cross-restart duplicate/idempotency guarantees.

**Blockers**

- **None that stop planning or coding.** The sandbox 401 on non-user scopes is the declared environment, not a gap: Flows 2–5 and the account-creation part of Flow 1 are **UNVERIFIED** (built in full, not runtime-confirmable). No required capability is missing from the SDK map — every flow maps to concrete operations.
- **Watch item (not a blocker): SDK target framework vs repo.** The Upvest SDK targets `netstandard2.0` and the eShop solution's `global.json` currently pins `8.0.x` (`rollForward: latestFeature`), while the task states a .NET 10 SDK with rollForward. `netstandard2.0` is referable from a .NET 8/10 project, so the `ProjectReference` to `plugins/upvest-v4/sdk/dotnet/src/UpvestInvestmentApi/UpvestInvestmentApi.csproj` should build; if the target runtime must be .NET 10, bump `global.json` accordingly. The reference is machine-local (points into this plugin's install path) — CI/teammates need the plugin installed and the reference re-pointed.
