# Upvest Investment API integration plan — eShopOnWeb managed portfolios

Provider: **Upvest Investment API .NET SDK** (`UpvestInvestmentApi`, APIMatic-generated), referenced from
`marketplace/plugins/upvest-v4/sdk/dotnet/src/UpvestInvestmentApi/UpvestInvestmentApi.csproj`.
Host: `src/PublicApi` (JWT-authenticated minimal endpoints, `IEndpoint<…>` pattern; EF persistence via `IRepository<T>`/`EfRepository<T>` over `CatalogContext`, in-memory when `UseOnlyInMemoryDatabase=true`).
All map facts below are grounded in `sdk/dotnet/sdk-map.md`, its `map/operations/*` pages, and the named `src/UpvestInvestmentApi/**` source files (paths are relative to the SDK root `marketplace/plugins/upvest-v4/sdk/dotnet/`). End-to-end sequencing is cross-checked against the Upvest Arazzo workflow packages in `repo/upvest-workflows/{user-onboarding,investment-solutions,payments}`.

## 1. Scope & sequence

The shop stores its own mapping records (new EF entities persisted through `IRepository<T>`): **Investor** (shop userId ↔ Upvest userId / accountGroupId / accountId / onboarding idempotency keys), **ModelPortfolio** (shop modelId ↔ Upvest allocationId), **Payment** (paymentId ↔ Upvest portfolio-order id + its idempotency key + euro amount), **Realignment** (realignmentId ↔ Upvest rebalancing-execution id). The signed-in shopper is identified from the JWT; every read/write is scoped to the caller's own Investor record.

**Flow 1 — Becoming an investor** (`POST/GET /api/portfolio/investor`)
1. `Users.CreateUser` — create the natural-person user (returns Upvest userId).
2. `UserChecks.CreateUserCheck` — submit the KYC/identity check (type `KYC`; carries the identityDocument fields). The arazzo also submits POR + INSTRUMENT_FIT; the shop submits at minimum KYC.
3. `UserIdentifiers.CreateIdentifier` — regulatory reporting identifier (skip for CONCAT nationalities AT/DE/FR/HU/IE/LU — Upvest auto-generates).
4. `TaxResidencies.SetTaxResidencies` — set the tax residency (taxId/taxCountry).
5. `AccountGroups.CreateAccountGroup` — type `PERSONAL` (returns accountGroupId).
6. `AccountsApi.CreateAccount` — type **`PORTFOLIO`** inside that group (returns accountId). This is the account "able to hold a managed portfolio".
7. `GET`: `Users.RetrieveUser` (+ `AccountsApi.RetrieveAccount`) to map the investor status (see enum mapping §2).

**Flow 2 — Model portfolios** (`PUT /api/portfolio/models/{modelId}`, `GET /api/portfolio/models`, `PUT /api/portfolio/investor/model`)
- First-time `PUT` of a modelId → `Portfolios.CreatePortfoliosAllocation`; subsequent `PUT` of a known modelId → `Portfolios.UpdatePortfoliosAllocation` (full replace). Shop maps modelId ↔ allocationId.
- `GET models` → `Portfolios.ListPortfoliosAllocations`.
- Investor model choice → `Portfolios.CreatePortfoliosConfiguration` (first choice) / `Portfolios.UpdatePortfoliosConfiguration` (switch) — links the investor's PORTFOLIO account to the allocation.

**Flow 3 — Paying in** (`POST/GET /api/portfolio/payments`)
1. Credit euros to the account group (sandbox funding, "whatever Upvest provides"): `VirtualCashBalances.CreateVirtualCashIncrease` (primary — directly credits the account group's cash). Alternative sandbox funding path: `Tests.CreateBankTransaction`.
2. Invest across the model's funds in their weights: `Portfolios.CreatePortfoliosOrder` (side `BUY`, `cash_amount`) — Upvest distributes the cash across the account's configured allocation. Refused unless the investor is accepted and a configuration (model choice) exists.
3. `GET payments` → `Portfolios.ListPortfoliosOrders` (filtered by `account_id`), newest first. Status mapping in §2.

**Flow 4 — Realignment** (`POST /api/portfolio/models/{modelId}/realignments`, `GET /api/portfolio/realignments/{realignmentId}`)
- `POST` → `PortfoliosRebalancing.TriggerPortfolioRebalancing` targeting the model's **allocation** (`Allocations` arm). Returns the rebalancing-execution id.
- `GET` → `PortfoliosRebalancing.RetrievePortfoliosRebalancingExecution` (identity/existence) **plus** `PortfoliosRebalancing.ListPortfolioRebalancingExecutionOrders` to derive status — the execution object itself carries **no status field** (see Assumptions §6).

**Flow 5 — The investor's portfolio** (`GET /api/portfolio`)
- `Portfolios.RetrievePortfoliosConfiguration` → modelId (allocation_id).
- `Valuations.GetAccountValuation` → holdings (`security_positions`: instrument + quantity + value) and totalValue (`total_security_value`). `paidIn` is the shop's own sum of invested payments (not an Upvest field).

A capability the map lacks (e.g. a single realignment status, a single "rejected" investor status) is recorded in Assumptions §6, not invented.

## 2. CONTRACT SHEET

> ⚠ **Signatures are generated code, verbatim.** Every operation that takes input takes **ONE request record** as its first parameter (an operation with no inputs takes none), built with an **object initializer whose property names are the record's own** (never flat positional arguments). The request record is the first arg; `RequestOptions? requestOptions = null` and `CancellationToken cancellationToken = default` follow.
> ⚠ **Every SDK type is written fully-qualified** with the namespace its source path implies (`Models/` → `UpvestInvestmentApi.Models`, `Models/Enums/` → `UpvestInvestmentApi.Models.Enums`, `Models/AnyOf/` → `UpvestInvestmentApi.Models.AnyOf`, `Requests/<Ctrl>/` → `UpvestInvestmentApi.Requests.<Ctrl>`, `Errors/` → `UpvestInvestmentApi.Errors`), taken from the path the map gives for THAT type — never from a neighbour.
> ⚠ **Every write's body member is OPTIONAL on the request record** (`… Body { get; init; }`, nullable) and **nothing but `IdempotencyKey` / path ids is marked `required`**. `required?` therefore selects almost nothing — the body IS the payload and MUST be set, and its own members carry the real `required` flags. Each write row names the body fields the endpoint needs.

### CROSS-OPERATION INVARIANTS

| Invariant | Operations | Enforced where |
|---|---|---|
| A fund `instrument_id` (ISIN) in a model `PUT` must be a tradable instrument Upvest offers | `CreatePortfoliosAllocation`/`UpdatePortfoliosAllocation` (10/11) ← `ListInstruments` (26) | endpoint handler for `PUT /api/portfolio/models/{modelId}`, before the SDK write — validate each requested ISIN against a `ListInstruments` read (the check is part of the work; the handler does not read instruments today) |
| The `modelId` an investor chooses must be one the shop's **ModelPortfolio** store defines (i.e. a modelId previously created via op 10/11 → allocationId) | `CreatePortfoliosConfiguration`/`UpdatePortfoliosConfiguration` (13/14) ← shop ModelPortfolio store (seeded by 10/11; mirror `ListPortfoliosAllocations` 12) | `PUT /api/portfolio/investor/model` handler, before the SDK write — resolve modelId→allocationId from the store; reject unknown modelId |
| The `allocation_id` passed to a configuration/rebalancing must be one `ListPortfoliosAllocations` returns | `CreatePortfoliosConfiguration` (13), `TriggerPortfolioRebalancing` (21) ← `ListPortfoliosAllocations` (12) | model-choice and realignment handlers — the shop's ModelPortfolio store is authoritative; it is reconciled against op 12 |
| `account_id` used in configuration/order/valuation must be the caller's own PORTFOLIO account | `CreatePortfoliosConfiguration` (13), `CreatePortfoliosOrder` (16), `GetAccountValuation` (24) ← caller's **Investor** store (seeded by `CreateAccount` 7, mirror `ListUserAccounts` 9) | every investor-scoped handler — take accountId from the caller's Investor record keyed by JWT identity, never from the request body |
| A pay-in requires an **accepted investor with a chosen model** (configuration exists) | `CreatePortfoliosOrder` (16) ← Investor status (op 2/8) + configuration (op 15) | `POST /api/portfolio/payments` handler, before funding + order — refuse if investor not active or no configuration |

⚠ The map never states these rules; they are derived from the task. "Operations" names the call that **defines** the legal set (a list/search, or the earlier write the shop stored); a single-item lookup is not a substitute.

## 3. Trap notes

- **Auth is two schemes at once (OAuth2 *and* HTTP message signing), and a missing signing key fails before the first byte** — wiring `OauthClientCredentials` alone leaves every call throwing. Cost: total outage that looks like a 401 but is not. **MUST load `upvest-v4:dotnet-authentication`.** (Flow 0 client wiring.)
- **Base-URL / server-node selection**: `Upvest:BaseUrl` must reach the right override point, and `ServerEnvironment.Production` is confusingly the **sandbox** host. Getting this wrong points sandbox traffic at live. **MUST load `upvest-v4:dotnet-configuration-resilience`.** (Flow 0.)
- **HttpClient ownership & client lifetime** for the singleton SDK client + DI registration — the options object is built once at registration. **MUST load `upvest-v4:dotnet-client-initialization`.** (Flow 0.)
- **AnyOf request bodies** (`UserCreateRequest`, `AccountCreateRequest`, `TriggerPortfolioRebalancingRequest`) and **union ids** (`InstrumentId`, `InstrumentUniqueIdentifier`): building the wrong arm, or reading a response union without `TryGet…`, silently serializes nothing or lands in the unknown arm. **MUST load `upvest-v4:dotnet-models`.** (Flows 1, 2, 3, 4.)
- **Open enums are not C# enums** — `Status`, `Status65`, `Status82`, `Side15`, `Currency` have no exhaustive switch; an unlisted wire value flows to `otherwise`. Mapping statuses by `==` to the five members silently drops new values. **MUST load `upvest-v4:dotnet-models`.** (Status mapping, Flows 1/3/4.)
- **Retries, total timeout budget, and pagination walking** — what `Retry.Timeout`/`StreamReadTimeout` actually bound, which verbs auto-retry, and how offset/limit pages terminate are not inferable from the signatures. **MUST load `upvest-v4:dotnet-configuration-resilience`.** (Flows with list reads + all writes.)
- **The per-call `Idempotency-Key` header is not the real key** — but these write records *do* carry a real caller-supplied `IdempotencyKey: Guid` member; its replay semantics (same key → original response replayed) govern retry/reconciliation. **MUST load `upvest-v4:dotnet-getting-started`** (Idempotency section) before relying on it. (Flow 3/1 reconciliation.)
- **Error surface**: every operation is Case A typed `ApiException<{Operation}Error>` with `TryGetNoContent`/`TryGetRawError`; a drifted 2xx or non-matching error body throws `ResponseDeserializationException` instead. **MUST load `upvest-v4:dotnet-error-handling`.** (All flows.)
- **Testing the SDK** (HttpClient stub seam, faking the clock, constructing SDK exceptions): **MUST load `upvest-v4:dotnet-testing`** before writing tests.

**UNKNOWN OUTCOMES** — connection can fail after Upvest may have acted.

All write idempotency keys are **derived deterministically** (`DeterministicGuid.Create(...)` from ids the shop already holds — shopUserId, PaymentId, RealignmentId, modelId — never `Guid.NewGuid()`), so "the stored key" is recomputed, not persisted, and a resend replays the original Upvest response.

| Write | The operation you re-read with | The reference you search by | Where in the code | The test that fails the connection |
|---|---|---|---|---|
| `CreateUser` | replay `CreateUser` with the derived key | `DeterministicGuid.Create($"{shopUserId}:user")` | `SignUpInvestorAsync` — mandatory `CallAsync` translates transport failure to `UpvestProviderException`; the Investor is only persisted after a 2xx, so a dropped send simply has no claim to leave behind | live-sandbox verified (`POST /users → 200`); scope-refused ops surface via the Case-A/auth path |
| `CreateAccountGroup` / `CreateAccount` | replay with derived key | `DeterministicGuid.Create($"{shopUserId}:group"|":account")` | `SignUpInvestorAsync` best-effort `TryStepAsync` — a non-success (incl. unknown) leaves the investor `pending`; the next `GET /investor` re-reads user+account status from Upvest | status re-read in `ReadInvestorStatusAsync` |
| `CreatePortfoliosAllocation` | derived key / `ListPortfoliosAllocations` | `DeterministicGuid.Create($"model:{modelId}:allocation")` | `UpsertModelAsync` `TryStepAsync` — the shop model is persisted regardless; allocation id stays null until a later upsert succeeds | — |
| `CreatePortfoliosConfiguration` | derived key / `RetrievePortfoliosConfiguration` | `DeterministicGuid.Create($"{shopUserId}:configuration")` | `SelectModelAsync` `TryStepAsync` | — |
| `CreateVirtualCashIncrease` | derived key | `DeterministicGuid.Create($"payment:{PaymentId}:fund")` | `PayInAsync` → `TryMoneyStepAsync`: an **answered** error marks the Payment `failed`; an **unknown** (null-status) outcome leaves it `pending` to be settled on the next GET | `TryMoneyStepAsync` (Answered vs. unknown) |
| `CreatePortfoliosOrder` | derived key / `ListPortfoliosOrders` | `DeterministicGuid.Create($"payment:{PaymentId}:order")` | `PayInAsync` → `TryOrderStepAsync`: answered-error → `failed`; unknown → Payment stays `pending`; status settled by `ReadPaymentStatusAsync` (re-reads the order from Upvest) on `GET /payments` | `TryOrderStepAsync` + `ReadPaymentStatusAsync` |
| `TriggerPortfolioRebalancing` | derived key | `DeterministicGuid.Create($"realignment:{RealignmentId}")` | `TriggerRealignmentAsync` → `TryRebalancingStepAsync`: answered-error → `failed`; unknown → `pending`; settled by `GetRealignmentAsync` → `DeriveRealignmentStatusAsync` | `TryRebalancingStepAsync` + `DeriveRealignmentStatusAsync` |

Each write settles its outcome in its own helper: an **answered** provider error records a terminal local state (`failed`), while an **unknown** (transport/timeout, null status) outcome leaves the Payment/Realignment `pending` and is settled on the next GET by re-reading Upvest — never reported as a hard failure when the connection dropped post-send. Derived idempotency keys make every replay single-acting.

## 6. Assumptions & Blockers

**Assumptions**

1. **Sandbox is authorised for user operations only** (per the task). Every non-user call in this plan — account/account-group creation, portfolio allocation/configuration/order, virtual-cash increase, bank-transaction simulation, rebalancing, valuation, positions, instruments, even some user-check/identifier/tax scopes — will return **401 "This client is not authorised to use these scopes"** in that sandbox. This is the environment, not a plan gap: every operation is still grounded and built in full, and the 401 is surfaced through the Case-A error path. *(Context, not a Blocker, as instructed.)*
2. **Investor status "rejected" has no direct Upvest field.** User `Status` is `ACTIVE`/`INACTIVE`/`OFFBOARDING`/`OFFBOARDED` only. The shop maps: account (PORTFOLIO) `ACTIVE` → `active`; user `INACTIVE` or account `PENDING_APPROVAL` → `pending`; `rejected` must be **derived** from a failed regulatory check via `ListUserChecks` (check result) — a shop-side decision. Recorded as `YOUR CALL — not in the map` on the status-mapping code.
3. **Realignment status has no direct Upvest field.** `TriggerPortfolioRebalancingResponse` carries only `id`; `PortfoliosRebalancingExecution` carries `id`/`accounts`/`allocations` but **no status**. The shop derives `pending`/`completed`/`failed` by walking `ListPortfolioRebalancingExecutionOrders` and aggregating the per-order `Status65` (all Filled/Settled → `completed`; any Cancelled → `failed`; otherwise `pending`). `YOUR CALL — not in the map`.
4. **Sandbox funding mechanism.** "Whatever Upvest provides" is taken to be `VirtualCashBalances.CreateVirtualCashIncrease` (directly credits the account group's cash), with `Tests.CreateBankTransaction` as the alternative. Both are grounded; the primary one is wired. If the tenant is not a vCash tenant, the credit-funding/direct-debit path (`CreditFundings`, `DirectDebits`) applies instead — confirm the tenant's configured funding method.
5. **One `Upvest:ClientId` serves both the OAuth2 `ClientId` and the signing `upvestClientId`.** The Arazzo packages distinguish the OAuth client id from the tenant `upvest-client-id` (both UUIDs). The task supplies a single `Upvest:ClientId`; the plan uses it for both. If the deployment's tenant client id differs from the OAuth client id, a separate config key is needed — surface to the user if signing fails with a client-id mismatch.
6. **`Upvest:SigningKeyPassphrase` may legitimately be empty** (unencrypted key). The fail-fast check treats "key present but passphrase intentionally blank" as valid only if the deployment declares the key unencrypted; otherwise blank passphrase is a misconfiguration. Decide at implementation.
7. **New EF entities** (`Investor`, `ModelPortfolio`, `Payment`, `Realignment`) are added to `CatalogContext`/`IRepository<T>` with `Infrastructure/Data/Config` configurations, following the existing entity/repository convention; duplicate refusal uses a PK/unique index, not the `CountAsync` read pattern. `YOUR CALL — not in the map`.
8. **`paidIn` (Flow 5) is the shop's own running total** of invested payments (sum of `Payment.Amount` for the investor), not an Upvest field.
9. **Model weights sum to exactly 100** is enforced shop-side before `CreatePortfoliosAllocation` (the `Allocation.weight` regex permits 0–100 per item but does not enforce the sum); Upvest also validates.

**Blockers**

None. Every flow maps to grounded operations; the sandbox scope restriction is expected environment behaviour, not a blocker.

## 8. Implementation resolutions (settling every `YOUR CALL — not in the map`)

- **Row 1 — startup fail-fast mechanism.** `ManagedPortfolioServiceCollectionExtensions.AddManagedPortfolio` binds the `Upvest:` section into `UpvestSettings` and runs `ValidateFailFast` **synchronously at registration** (inside `ConfigureServices`, before `app.Run`). It throws `InvalidOperationException` naming any missing key (`Upvest:ClientId/ClientSecret/SigningKeyId/SigningKeyPath/SigningKeyPassphrase/BaseUrl`), never echoing a value, and rejects a non-absolute `BaseUrl`. Verified: the host refuses to boot with a missing key; with all keys present it boots and signs (`POST /users → 200` against the sandbox).
- **Row 2 — secret sourcing & rotation.** Secrets come from `IConfiguration` (user-secrets in dev, env/secret-store in prod). `AddUpvestInvestmentApiClient`’s options callback runs **once at registration** and the singleton `UpvestInvestmentApiClient` captures the OAuth creds + signing hook; a rotated `ClientSecret`/`SigningKeyPassphrase` takes effect only on **process restart** (documented, restart-required).
- **Row 6 — observability / log levels.** `ILogger<UpvestManagedPortfolioService>`: Information for the request line (via the SDK’s built-in logger, URL redacted by allow-list), Warning for an answered provider error (`operation`, `StatusCode`, `Method`, `RequestUri` — **never** a request body) and for skipped best-effort steps, Error for `AuthSchemeException`. `LogRequestBody` stays **off** and `LoggerFactory` is filled from the host container (disarming the `UPVEST_INVESTMENT_API_LOG` trace path). Verified: no personal data in logs.
- **Assumption 2 — investor status mapping.** `ReadInvestorStatusAsync`: user `ACTIVE` **and** PORTFOLIO account `ACTIVE` → `active`; user `OFFBOARDING`/`OFFBOARDED` → `rejected`; otherwise (incl. a status that cannot be read) → `pending`. Status is read back from Upvest (`RetrieveUser` + `RetrieveAccount`), arm-agnostic across the TOL/BYOL AnyOf (`TryReadUser`).
- **Assumption 3 — realignment status mapping.** `DeriveRealignmentStatusAsync` walks `ListPortfolioRebalancingExecutionOrders` (the execution carries no status), aggregating per-order `Status71`: all `FILLED` → `completed`; any `CANCELLED` → `failed`; otherwise, or when the page walk is capped, → `pending`.
- **Assumption 7 — new EF entities.** `Investor`, `ModelPortfolio` (+ `ModelFund`), `Payment`, `Realignment` added to `CatalogContext` via `IRepository<T>`/`EfRepository<T>` with `Infrastructure/Data/Config/PortfolioConfiguration.cs`. Duplicate refusal uses a **natural primary key** (`ShopUserId`, `PaymentId`, `RealignmentId`) — refused even by the in-memory provider — not the `CountAsync`-then-add pattern.
- **Assumption 8 — paidIn.** `ComputePaidInAsync` sums `Payment.Amount` over the caller’s payments that were not locally marked `failed` (the shop’s own running total; not an Upvest field).

Sandbox note (verified): the client is authorised for user operations only, so `CreateUser` succeeds (`200`) while scope-bound operations (checks, identifiers, tax, account groups, accounts, portfolios, virtual cash, rebalancing, valuation, instruments) are refused at the OAuth token step (`auth/token → 401`). Every flow is built in full and the refusal is surfaced through the error boundary exactly as designed.
