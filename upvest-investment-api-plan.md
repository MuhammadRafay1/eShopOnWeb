# upvest-investment-api-plan.md — Managed investment portfolios for eShopOnWeb

Integration of the **Upvest Investment API .NET SDK** (`UpvestInvestmentApi`, root namespace) into `src/PublicApi`, adding managed investment portfolios as an **additive** capability beside the existing catalog/basket/order flow. Written per `dotnet-integrate-upvest-investment-api`; every contract fact below was read this session from the SDK map at `plugins/upvest-v4/sdk/dotnet/` (`sdk-map.md` + `map/operations/*`) and the source files those pages name. Paths in **source** cells are relative to that SDK root.

> ⚠ **Sandbox reality that shapes this whole plan.** The task states the sandbox client is authorised **only for USER operations**; any other scope is refused with `401 "This client is not authorised to use these scopes"`. Of the operations below, only `Users.CreateUser`, `Users.RetrieveUser`, `Users.ListUsers` carry `users:*` scopes. **Every other operation — accounts, portfolios, topups, positions, valuations, instruments, rebalancing — will be rejected at the provider in sandbox.** This is the environment, not a defect. All five flows are built in full; verification stops where sandbox authorisation stops. See **Assumptions & Blockers**.

## 1. Scope & sequence

Domain mapping discovered from the map (the task's vocabulary → Upvest's):

| Task concept | Upvest concept | Operations |
| --- | --- | --- |
| Investor (shopper signed up at Upvest) | **User** (TOL operating model) | `Users.CreateUser`, `Users.RetrieveUser` |
| Investor's account that holds the portfolio | **Account** (+ its account group) | `AccountsApi.CreateAccount`, `AccountsApi.ListUserAccounts`, `AccountsApi.RetrieveAccount` |
| Model portfolio (name + funds + weights) | **Portfolio allocation** | `Portfolios.CreatePortfoliosAllocation`, `Portfolios.UpdatePortfoliosAllocation`, `Portfolios.ListPortfoliosAllocations` |
| Which model an investor follows | **Portfolio configuration** (account → allocation) | `Portfolios.CreatePortfoliosConfiguration`, `Portfolios.UpdatePortfoliosConfiguration`, `Portfolios.RetrievePortfoliosConfiguration` |
| Paying money in | **Top-up** (cash in) + **portfolio order** BUY (invest across funds) | `TopUps.CreateTopup`, `TopUps.ListTopups`, `Portfolios.CreatePortfoliosOrder` |
| Realignment | **Portfolio rebalancing execution** | `PortfoliosRebalancing.TriggerPortfolioRebalancing`, `PortfoliosRebalancing.RetrievePortfoliosRebalancingExecution` |
| Portfolio holdings & value | **Account valuation** (+ positions) | `Valuations.GetAccountValuation`, `Positions.ListPositions`, `Portfolios.RetrievePortfoliosConfiguration` |
| Fund ISIN legal set | **Instruments** | `Instruments.ListInstruments` |

Implementation steps, in order:

1. **Infrastructure wiring.** Register the `UpvestInvestmentApiClient` (singleton, DI) bound from the `Upvest:` config section; add the signing hook; set base URL and environment. Register a **new, PublicApi-owned EF DbContext** for the local investment records (the task requires PublicApi to have its own isolated store). *MUST load dotnet-client-initialization, dotnet-authentication, dotnet-configuration-resilience.*
2. **Local persistence model.** Entities for: investor link (eShop user identity → Upvest `user_id`/`account_id`/`account_group_id` + last-known status), model portfolios (local `modelId` → Upvest `allocation_id` + name + funds, so the app owns the model set), payments (local `paymentId` → Upvest topup id / order id + amount + status), realignments (local `realignmentId` → Upvest execution id + status). In-memory EF (`UseOnlyInMemoryDatabase=true`), isolated to PublicApi.
3. **Flow 1 — Becoming an investor.** `POST /api/portfolio/investor` → `Users.CreateUser` (TOL body) then `AccountsApi.CreateAccount`; store the link; `GET /api/portfolio/investor` → `Users.RetrieveUser` (+ account readiness) and report status.
4. **Flow 2 — Model portfolios.** `PUT /api/portfolio/models/{modelId}` (admin) → create-or-replace via `Portfolios.CreatePortfoliosAllocation` / `Portfolios.UpdatePortfoliosAllocation`; validate weights sum to exactly 100 before the call. `GET /api/portfolio/models` → `Portfolios.ListPortfoliosAllocations` (or the local store). `PUT /api/portfolio/investor/model` → `Portfolios.CreatePortfoliosConfiguration` / `UpdatePortfoliosConfiguration`.
5. **Flow 3 — Paying in.** `POST /api/portfolio/payments` → refuse unless investor accepted AND a model chosen; then `TopUps.CreateTopup` (money in) + `Portfolios.CreatePortfoliosOrder` BUY (invest across funds per the allocation's weights). `GET /api/portfolio/payments` → `TopUps.ListTopups` / local payments, newest first.
6. **Flow 4 — Realignment.** `POST /api/portfolio/models/{modelId}/realignments` (admin) → `PortfoliosRebalancing.TriggerPortfolioRebalancing` (Allocations arm = `[allocationId]`). `GET /api/portfolio/realignments/{realignmentId}` → `RetrievePortfoliosRebalancingExecution` (status derivation: see trap/blocker).
7. **Flow 5 — The investor's portfolio.** `GET /api/portfolio` → `Portfolios.RetrievePortfoliosConfiguration` (model followed) + `Valuations.GetAccountValuation` (holdings: instrument/quantity/value, total value); `paidIn` = sum of the caller's payments.
8. **Error boundary, polling, status reconciliation, tests.** *MUST load dotnet-error-handling, dotnet-models, dotnet-testing.*

Every status the app reports (sign-up, payment, realignment) is derived from a fresh read of the provider (polling) — the app exposes no webhook route.

## 2. CONTRACT SHEET

> ⚠ **Signatures below are generated code, copied verbatim.** Each operation that takes input takes **ONE request record as its first parameter** (plus optional `RequestOptions? requestOptions = null, CancellationToken cancellationToken = default`); build the record with an **object initializer using the record's own property names** — never flat positional arguments. An operation with no inputs takes no record.
> ⚠ **Every SDK type is fully-qualified from the namespace its source path implies** (`Models/` → `UpvestInvestmentApi.Models`; `Models/AnyOf/` → `UpvestInvestmentApi.Models.AnyOf`; `Models/Enums/` → `UpvestInvestmentApi.Models.Enums`; `Requests/<Ctrl>/` → `UpvestInvestmentApi.Requests.<Ctrl>`; `Errors/` → `UpvestInvestmentApi.Errors`). Take each type's namespace from the path the map gives for **that** type, never from a neighbour.

**All operations are Case A (typed error), throw-based, no pagination variant (single response), server group `Default`.** Every error row is the same shape: `ApiException<{Operation}Error>` with `TryGetNoContent([NotNullWhen(true)] out RawError? value)` over the listed statuses, plus `TryGetRawError([NotNullWhen(true)] out RawError? error)` fallback. `{Operation}Error` lives at `src/UpvestInvestmentApi/Errors/{Operation}Error.cs`.

| Invariant | Operations | Enforced where |
| --- | --- | --- |
| `modelId` on `PUT /investor/model`, `POST /payments` (via config), `POST /models/{id}/realignments` must be a model the operator created (its `allocation_id`) | `CreatePortfoliosConfiguration`/`UpdatePortfoliosConfiguration` & `TriggerPortfolioRebalancing` ← `Portfolios.ListPortfoliosAllocations` (or the local models store, which records each `allocation_id` returned by `CreatePortfoliosAllocation`) | Look up `modelId` in the local models store (mirror of `ListPortfoliosAllocations`) and 404 if absent, before calling configuration/rebalancing |

## 3. Trap notes

- **T1 — Investor fields with no `UserTolCreateRequest` member.** The task's `taxId`, `taxCountry`, and `identityDocument {type,number,issuingCountry,expiryDate}` are **not** top-level members of `UserTolCreateRequest`. **DECIDED (implemented):** these are the shop's own KYC/verification artifacts; they are **persisted locally** on `InvestorRecord` (the shop's record of what it checked) and **not** injected into the TOL body as unmodeled fields (which the provider could reject). `taxCountry` is used to derive the required `Fatca.Status` (`true` iff `US`), with `Fatca.ConfirmedAt = now`. The two optional consent objects (`TermsAndConditions`, `DataPrivacyAndSharingAgreement`) are **omitted** because they require a pre-registered `consent_document_id` the form does not carry and we must not fabricate. Verified live: `CreateUser` returns `200` against the sandbox with this body. (`UserGateway.CreateUserAsync`, `InvestorRecord`.)
- **T2 — Investor/account status is a union read, not a flat field.** `UserGetResponse`, `UserCreateRequest1`, `AccountCreateResponse`, `AccountRetrieveResponse` are all `AnyOf` unions; the status that maps to `pending/active/rejected` is inside the matched arm. Reading it wrong compiles but returns the wrong status. *MUST load dotnet-models.*
- **T3 — Money is a decimal STRING on the wire, a JSON number in our API.** Every Upvest amount/quantity/weight/value (`cash_amount`, `TotalSecurityValue.Amount`, `Value`, `Quantity`, `Weight`) is a regex-constrained decimal string; the task fixes our response amounts as JSON numbers, two decimals, euros. Converting loses or gains precision if done naively, and an amount that violates the SDK regex is rejected. *MUST load dotnet-models.*
- **T4 — A top-up is not settled cash by itself.** `PaymentsTopupsResponse` returns a `SettlementReference` and status `Confirmed` — real funding needs a SEPA transfer; status reaches `Settled` only after money arrives. How the sandbox settles a top-up (or whether the portfolio order can run before settlement) changes the payment flow. *MUST load dotnet-calling-endpoints.*
- **T5 — Realignment execution carries no status.** `PortfoliosRebalancingExecution` has only id/timestamps/accounts/allocations — there is no `status` member to map to `pending/completed/failed`. ## 6. Assumptions & Blockers

**Blockers**

- **B1 — Sandbox authorises USER scopes only.** The task states the sandbox client is authorised only for USER operations; everything with `accounts:*`, `portfolios:*`, `topups:*`, `positions:*`, `valuations:*`, `instruments:*` scopes returns `401 "This client is not authorised to use these scopes"`. So Flow 1's `CreateUser`/`RetrieveUser` can be verified live, but **account creation and all of Flows 2–5 cannot complete against sandbox.** Per the task this is expected: build every flow in full, verify as far as sandbox allows (the 401 path and the local-store/validation logic are verifiable; the provider happy-path is not). The error boundary must treat this 401 as a configured-but-unauthorised condition, distinct from a missing credential.
- **B2 — Realignment status has no provider field.** `PortfoliosRebalancingExecution` exposes no `status`; the task's `GET /realignments/{id}` must return `pending → completed/failed`. Resolution must derive status from `ListPortfolioRebalancingExecutionOrders` (the execution's order statuses) or from a local pending→terminal transition. This derivation is unverifiable in sandbox (B1) and its exact mapping is **UNVERIFIED** (only live traffic settles which order-status combination means `completed` vs `failed`). Recorded as a defensive directive: treat a freshly-triggered execution as `pending`, derive terminal state from the execution orders, and default to `pending` on ambiguity.
- **B3 — Settlement/order sequencing in sandbox is UNVERIFIED (T4).** Whether a `CreatePortfoliosOrder` can be placed before a top-up reaches `Settled`, and how the sandbox simulates incoming cash, cannot be confirmed from the map. Code defensively: record the payment as `pending` after `CreateTopup`+`CreatePortfoliosOrder`, and move it to `invested`/`failed` only from a subsequent poll of the order status (`Status65`).

**Assumptions**

- **A1 — Investor = TOL user.** The task's KYC fields (name/email/birth/nationality/address/identity doc) match the TOL operating model, so `CreateUser` uses `UserTolCreateRequest` (not BYOL). If the client is configured for BYOL, switch the arm.
- **A2 — "Paying in" = top-up (cash) + portfolio order BUY (invest).** `CreateTopup` credits cash; `CreatePortfoliosOrder` side `BUY` invests that cash across the account's current allocation weights. `GET /payments` surfaces the cash-in records (`ListTopups`) joined with their order/local status.
- **A3 — The app owns the model set in its local store.** Each `PUT /models/{modelId}` maps a caller-chosen local `modelId` to an Upvest `allocation_id`; `GET /models` can serve from the local store (authoritative for what the operator offers) or mirror `ListPortfoliosAllocations`. The cross-operation `modelId` invariant is enforced against this local store.
- **A4 — PublicApi gets its own isolated in-memory store.** The task says PublicApi has its own isolated store, so a **new DbContext** (separate from `CatalogContext`) is registered in PublicApi, using `UseInMemoryDatabase` gated by `UseOnlyInMemoryDatabase=true` (mirroring `src/Infrastructure/Dependencies.cs`). Name is `YOUR CALL`.
- **A5 — Current investor identity.** The signed-in shopper is taken from the JWT `ClaimsPrincipal` (name/email claim) injected into each endpoint handler; all account/user ids are resolved from that caller's stored investor-link only, never from the request body (enforces "one shopper never sees another's data"). PublicApi endpoints do not currently read `ClaimsPrincipal`, so this is a new pattern — `YOUR CALL`.
- **A6 — `accountGroupId` sourcing.** Top-ups key on `account_group_id`; account creation/`ListUserAccounts` yields both the account and its group. The exact field path on `AccountCreateResponse` was not read this session (T6) and must be confirmed in-file before use.
- **A7 — Money conversion.** Our API uses JSON numbers in euros, two decimals; the SDK uses decimal strings. Convert with fixed-point formatting (`F2`/`decimal`), never `double`, to satisfy both the task's two-decimal rule and the SDK regexes (T3).

**Decisions settled during implementation** (were `YOUR CALL — not in the map`):
- **T1** tax/identity-document mapping — persisted locally on `InvestorRecord`, not sent as unmodeled TOL fields; `taxCountry` drives `Fatca.Status`; consents omitted (no `consent_document_id`). See T1 above.
- **A4** DbContext — `PortfolioContext` (namespace `…PublicApi.Portfolio.Data`), PublicApi-owned, registered in `PortfolioServiceCollectionExtensions.AddManagedPortfolios`; in-memory database name `"PortfolioDb"` when `UseOnlyInMemoryDatabase=true`, otherwise `UseSqlServer("PortfolioConnection" ?? "CatalogConnection")`.
- **A5** current-user identity — `EndpointSupport.GetShopperId` reads `ClaimTypes.Name` (falls back to `Identity.Name`) from the JWT `ClaimsPrincipal`; account/user ids are resolved only from that caller's own `InvestorRecord`, never the request body.
- **#1** credential fail-fast — `AddManagedPortfolios` binds `Upvest:` via `AddOptions<UpvestSettings>().ValidateDataAnnotations().Validate(File.Exists(SigningKeyPath)).ValidateOnStart()`; `[Required]` on every part incl. empty-string rejection (passphrase excepted, may be blank). Caveat: a clean host with no `Upvest:` config refuses to boot — intentional for prod; in this repo the config comes from user-secrets.
- **#3** timeout budget — SDK `Retry.Timeout = 15s` (per attempt) + named `HttpClient.Timeout = 30s` (per attempt backstop); whole-call budget is the ASP.NET request `CancellationToken` (`HttpContext.RequestAborted`) flowed endpoint → service → gateway → SDK on every call.
- **#4** write-retry — SDK defaults kept (`POST` never auto-resent; `PUT` is): acceptable because every create/trigger write carries a persisted `IdempotencyKey` reused on retry, and `UpdatePortfoliosAllocation` is a full-replace reconciled by re-read.
- **#6** observability — provider failures logged at Warning with operation name + status (and unauthorised-scope / unknown-outcome reason); state transitions at Info; request bodies never logged (`LogRequestBody=false`, `LoggerFactory` set explicitly).
